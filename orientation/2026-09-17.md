Follow [the sprint record](../sprints/2026-09-17.md) for current work; this orientation retains the evidence scope of its original source pass.

My working interpretation: the suite has substantial semantic and implementation material, while the missing connections between selected pieces often determine whether a complete experience exists. That is an inference from this bounded inspection, not a census of all code quality.

## Five findings that change what to do next

### 1. A document demo is not yet a persistent community workspace

The desktop's edit path changes document history, writes/reseals the cell heap out of band, saves its layout sidecar, then attempts a revision SetField turn. The heap write itself is not an ordered executor effect. On a durable World, a prior committed turn touching that cell makes the heap setter refuse; the short-circuit then skips the revision turn. The source explicitly records the second-save consequence.

This is narrower and more useful than either “the desktop is finished” or “the document system is fake.” The existing ephemeral author/fork/conflict/resolve test is a valuable behavior specification. A product closure condition is repeated edits plus restart/replay through the chosen canonical storage/turn path, with the document body and its receipt agreeing and refusal leaving committed state unchanged.

See graph records C-DOC-DURABLE and W-DOC-PERSIST; research/resources.md contains the path-by-path trace. This pass read code and tests; it did not run them.

### 2. Minidregg's central question is which semantic object its consumers use

D-0002 selects canonical typed cell effects and flat hyperedges. Compiler/DeclaredHyperedgeArtifact still imports the older DeclaredHyperedge carrier, while TypedCellHyperedge explicitly identifies that older carrier's restricted schema. The September kernel audit is therefore not merely an old mood about code quality: the concrete compiler dependency remains visible.

The current consumer follow-up makes the conclusion precise: Compiler already consumes typed Theory-level authorization, effect, cell/materializer and canonical-transition data. Typed joint carriers have real Hyperdocument and Assurance consumers. The unresolved connection is the joint-turn artifact projection specifically. Existing proven components may remain valuable; the choice is per semantic carrier and consumer.

See C-KERNEL-COMPILER and W-CANONICAL-CONSUMER. The scope is this compiler projection; this is not a claim that no typed-state component has any compiler consumer.

### 3. Proof research contains concrete deliverables and concrete remaining obligations

The September IR2 directory retains a source-hashed patch and check records targeting a particular minidregg revision. Its actual-row FRI theorem has a specific conditional experiment and bound. Its own handoff separately names packed-commitment extraction, false PCS claims to farness, challenge-generation transport, and implementation refinement.

These are different tasks from parameter tuning, a generic “make STARKs sound,” or displaying a suite identifier. A research package can be available for integration while its deployed acceptance claim remains open. No cryptographic strength number is carried into this orientation as an end-to-end system guarantee.

See C-IR2-PACKAGE, C-IR2-BOUNDARIES, and research/kernel.md.

### 4. There are multiple partial routes to the inhabited world

DreggCloud's July Expedition record describes signed membership, actual HTTP operations, archive custody, and restart/replay. Its semantic House workroom proposal describes the broader observe → work → propose → review → authorize → land journey, but explicitly says that House integration is absent.

The deos desktop supplies authoring and inspectability concepts relevant to the desired medium. Agent-platform supplies a different hosted grain journey. External Hermes ACP integration and the compiled Rust brain in the confined host are also distinct paths.

A further source trace found a specific authoring split: ModeCardSurface buttons/binds operate on an AttachedApplet over the cockpit World, while its CardEditor owns a separately minted portable applet. Editing the view repaints the pane but does not itself persist that amended manifest into the focused World cell. The ordinary Hermes MCP server startup likewise does not configure the available live-World socket bridge. These are concrete questions about which state an action actually changes, not simply missing UI polish. See research/authoring.md and C-CARD-IDENTITY / C-MCP-WORLD.

The operations agent's House recommendation is retained in its research note as an attributed proposal, not adopted as the product architecture. The initial instruction was inventory first; the later nexus direction now motivates comparing authority, durable state, participant-operated hosting, user experience and integration work across those paths.

### 5. Local-first has another existing foundation to evaluate

cv recovered ~/dev/leanuweave. Its current README and manifests describe a standalone coordination/history library and Lean-to-native decision kernels; historical user instructions explicitly ask for replicated computations, choreography, sequence CRDTs, and ERA. It is not the proof system formerly called Loom in minidregg.

There is already an uncommitted Uwueave Projection V2 experiment in minidregg. It renders neutral coordination data into Rust and has static-data tests; it is not an admission, proof-verification, scheduling-permit or resource-runtime integration. The cross-repository contract explicitly says V2 is not the default new crossing and should not be merged merely because its data is well formed. This is an existing integration attempt to account for, not a reason to invent another adapter.

Before designing another synchronization abstraction, compare its actual contracts with minidregg hyperdocuments and breadstuffs branch/stitch. No semantic consumer cutover or general compatibility has been established here. See research/current-consumers.md.

## How assortia should earn its keep

Start with a small set of capability questions. For each, retain:

1. intent and the person/session that established it;
2. scoped assertions about the semantic object, implementation, and receiving consumer;
3. exact source or execution evidence and its revision/configuration;
4. decisions, competing proposals, and unresolved questions;
5. work that would close a particular missing connection.

A claim should be an object in the graph, so two scoped assertions can coexist. “Built” cannot be a single field on a project: a replacement proof can exist, remain unconsumed, and have no deployment at the same time. An absence of a graph edge means not yet established by this map.

The small JSON-LD specimen has stable local URN identities and source hashes. It is meant to test those questions before choosing a database, ontology, or editing UI. Its human-readable reports are dated; freshness checks never silently turn old prose into a current verdict.

Not every discrepancy deserves a ticket. Promote one when it blocks an intended experience, misstates a load-bearing guarantee, causes repeated work, or changes a decision. Archive incidental observations without demanding that ember triage them all.

## Git, Fossil, and fleet work

Git remains the code and artifact history. Fossil can be evaluated as a separate collaboration repository for issues, discussion, decisions, and project notes that link to Git revisions and assortia records. This does not require importing all Git histories into Fossil.

Fossil supports custom ticket fields and reports, and configurable links to other sites/repositories. Those external links do not create backlinks automatically. The graph would therefore still need explicit consumer/evidence relationships. This pass read the official documentation; no Fossil service or integration was installed or exercised.

cv already exposes a fleet-task substrate, including review and Git-observed landing. It deserves evaluation before inventing another agent dispatch/landing ledger. Its existence does not establish that it is currently used for this suite.

Whichever tools we select, decide where each fact is maintained: issue status in the tracker, evidence/claim identity in the graph, source history in Git, session provenance in cv. Other views should point to or derive from those records.

Official references: [ticket customization](https://fossil-scm.org/home/doc/trunk/www/custom_ticket.wiki), [interwiki links and their limits](https://fossil-scm.org/home/doc/trunk/www/interwiki.md).

## Current investigation questions

1. Which existing resource identities and semantics should be unified, and which are intentionally distinct? Compare live World, portable applet, House projection, typed joint commit, and native artifact.
2. For each reachable operation, which exact state changes and what survives a second operation, process restart, local fork, or remote delivery?
3. Which current compiler/adapter accepts each semantic artifact? Which replacements are proved, available as patches, imported, or actually consumed?
4. What job classes already have an objective result checker or a bounded dispute relation? Which merely record a provider's assertion?
5. Where do provider resources, identities, budgets, token custody and penalties become real operations rather than fields or descriptions?

These questions began as candidate investigations; the subsequent autonomous sprint now uses them to select coherent implementation bundles. Product utility, semantic fidelity, cryptographic assurance, and operational durability must not borrow completion from one another.

Its scope and architecture are proposals; the source findings above have not become implementation closures.
