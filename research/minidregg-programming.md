# What can actually be programmed in minidregg? — bounded source pass

Source-only, 2026-09-17. Reused previously read CLAUDE/ATLAS/PROJECT and assortia orientation. No builds, execution, git operations or sibling edits. The closed Hyperdocument action grammar is **not** the boundary of kernel programmability. Three concrete candidates follow. Paths below are relative to `/Users/ember/dev/minidregg`.

## 1. Data-authored atomic action batches — best first small semantic execution check

**Program value:** `Theory/DeclaredActionLowering.lean:44` defines first-order `Action.create`, `write` with expected old value, and `move` with explicit account/resource/expected balances/amount. `Declaration` at :234 contains a complete ordered action list, schema version, expected pre-root and nonce. This is user-selectable program data, although no interactive authoring client was located in this bounded pass. It is straight-line guarded effect programming, not general-purpose computation.

**Request → evaluation → effect:** `RequestContext.request` at :395 derives the exact authority request from that declaration, choosing mutateObject/transfer/installProgram by target kind and binding arguments/effects/pre-root/cost. `runCheckedWrites` at :79 interprets the ordered guards and writes; `Declaration.patch` at :295 derives the canonical patch from the same actions. `ValidAt` (:418) binds successful guard execution to that exact post, and `Accepted`/`accept` (:445/:454) combine it with authorization and `AcceptedCellEffect`. `accept` is noncomputable proof-level construction, not an immediately callable native shell admission endpoint.

**Actual receiving consumers:** `Compiler/DeclaredActionBytes.lean:43` decodes the declaration and rejects malformed/version-mismatched/empty batches. `Compiler/DeclaredActionAir.lean:380` emits a statement-specific descriptor, with `descriptor_accepts_iff_run` at :412; this is the action-guard seam, explicitly not the policy verifier. `Kernel/DeclaredActionExecution.lean:42` packages the accepted effect into a leg, :136 constructs `typedCommit`, and :211 constructs `durableIntent` with exact receipt/charge/nullifier. Its `multiDeclaration`/`multiCompilerAccepts`/`multiHyperedge_nonempty` examples at :279/:320/:330 are source witnesses. Imports into umbrellas exist, but the source census located no external importer of `DeclaredActionExecution` beyond Kernel.lean, and no Rust action-batch native endpoint. Its `projection` (:37) is constant in a supplied authState, so it is not evidence that a chosen runtime authenticates that projection from its actual storage.

**Exact missing join:** practical versioned source bytes and authoring transport → executable authorization/admission against actual canonical authority state → actual durable handler/refinement and user-visible returned receipt. The current lawful codec is **unary** (`List.replicate (declaration.code + 1) 0`, Theory/DeclaredActionLowering:271), using nested pairing codes. Do not attempt a realistic canonical byte roundtrip casually: even tiny-looking identifiers/programs can generate enormous byte arrays. `programCode` is an integer field; storing it / selecting installProgram does not establish later execution of arbitrary code.

**Recommended next check, not performed:** a tiny scratch Lean exercise importing only `Theory.DeclaredActionLowering`, evaluating two user-chosen `runCheckedWrites` programs against an empty finite store: create x=3 then guarded write 3→4 succeeds with x=4; the same program expecting x=2 refuses. Add an ordered second write to show actual composition. Do not call the unary declaration encoder. Follow with a narrow check of the existing typed-commit witness once dependencies/olean state are known. This establishes a real executable data-programming primitive; it does not establish cryptographic authority, shell installation or durability. It is more informative for the current programming question than rerunning a fixed native arithmetic vector.

## 2. Data-authored policy rules — real compiled admission, practical codec still open

**Program value:** `Pred/Core.lean:119` defines a first-order predicate tree over named old/new scalar slots: equality, order, membership, write-once, monotonicity, witnessed identifier and Boolean composition. `evalWith` at :231 is the reference interpreter; `eval` at :266 uses the fail-closed discharge oracle. `Compiler/CanonicalPolicyAdmission.lean:36` stores the predicate in a versioned `PolicyRecord` with policy ID/domain/semantics/previous address.

**Request → evaluation → effect:** `CanonicalPolicyConfig.verifies` (:82) resolves request.policyId/epoch, checks exact record/address/domain/semantics and old-state/effects digests, then checks `PredCompile.lower`, not an independent host policy evaluator. `Compiler/PredCompile.lean:365` lowers the tree; :373 supports equality/membership/writeOnce/witnessed/Boolean closure but **refuses le and monotone**. Witnessed is supported with the fail-closed first-party meaning; this is not evidence of an installed arbitrary external discharge portal. Injective field interpretation is a checked premise. `CanonicalPolicyAdmission.admit` (:237) joins membership/current epoch and compiled acceptance into `Authorized`. Policies constrain a candidate transition; they do not generate its effects by themselves.

**Actual receiving consumers:** `Kernel/CanonicalPolicyRegistry.lean:191` provides exact selected payload; `:299` guards its registry root through `DurableDataIntent`. `Compiler/CredentialAuthorityPolicyRegistry.lean` concretely joins a four-slot authority page, selected source, authorization and guarded settlement (`positiveAuthorized`:379, `selectedPayload`:413, `guardedIntent`:468). These are actual Lean consumers, stronger evidence than merely an unused AST.

**Exact missing join:** an executable practical source codec/authoring installation path and a physical receiving store. The latter file's `policyRecordCodec` (:77) is **noncomputable**, constructed from `Encodable.ofCountable`, and many selected-page examples are noncomputable. Its own opening scope explicitly leaves signatures and physical `ImplementationRefinement` outside the model. Therefore the page/selection construction is not proof that friends can currently upload a new policy and have a running node enforce it. A useful shell route could program permitted changes through these rules, but must select the supported fragment or extend its compiler before promising order predicates.

## 3. Fueled bytecode computation — actual interpreter, but native consumer specializes one program

**Program value/evaluation:** `Theory/EvmFragment.lean:98` takes code and calldata lists, interpreting STOP, ADD, CALLDATALOAD, MSTORE, PUSH1 and RETURN with stack/memory behavior; unsupported opcodes refuse. `exec` (:124) has explicit fuel and `evmRun` (:133) starts the machine. Thus it genuinely accepts caller-selected code data within this fragment; the interpreter is not merely a hand-named arithmetic function. `fragmentCode` (:143) selects the particular 15-byte calldata-add program used by the following specialization.

**Compiler → real native consumer:** `Compiler/EvmAddAir.lean` specializes that fragment through the residual arithmetic relation. `Compiler/EvmStage0NativeDeployment.lean:403` defines controller input **Claim(X,Y,Z)**, :411 issues native bytes and checks replies with the existing Lean descriptor checker. :157 builds the instruction and :549 its DeploymentJoin; the generated artifact is included by `prover/src/lib.rs:33`. `prover/src/native_dispatch.rs:261` implements `evm_stage0_add_aux_bytes`, executing emitted rows; `prover/tests/evm_stage0_dispatch.rs:140` compares dispatch output against retained Lean-written vectors. These are source paths and test assertions, not a newly observed pass.

**Effect boundary / exact missing join:** work 9103 is a **fixed u256-add auxiliary generator**, not a native entry accepting arbitrary uploaded EVM bytecode. Its input is operands/claimed result; no arbitrary code argument is in the controller Claim. The reviewed route certifies arithmetic response, not an authorized resource mutation, storage update or programmable nexus tool installation. To use it as the shell's computation substrate requires an explicit selected-language compiler/controller for submitted programs and an accepted cell-effect/output publication consumer. The existing byte interpreter can be tested now; calling the specialized native route “the programmable kernel shell” would overstate its scope.

## Interpretation for the mixed application

These candidates support a mixed programmable environment without requiring one first app: compose user-selected guarded actions, user-authored admissibility rules and bounded checked computation. They have different maturity and should not be collapsed into a claim of either “no programmability” or “the shell already exists.” `Theory/IndexedProgram.lean:54` also supplies free indexed programs and `interpret` (:192), but its generic handler/continuation model and demo are not evidence of an external serialized user-program evaluator; I did not promote that abstraction into a fourth product candidate.

The first useful execution check is candidate 1's tiny action interpreter, followed by the exact admitted/receiving path. The implementation choice remains open until the actual shell request → authority → program → canonical effect → durable acknowledgment route is selected. No new programming language or second semantics is proposed here.
