# Android/mobile inventory (source at 2026-09-18)

Bread contains Android experiments, but no current Kotlin/Gradle product app or JNI embedding layer.

- `breadstuffs/mobile/deos-core-smoke/` is a standalone Rust executable over `dregg-turn` and `dregg-cell`. Its documented command is `cargo ndk -t arm64-v8a build -p deos-core-smoke`, then `adb push`/execute. `RUN-OUTPUT.txt` records a 2026-06-25 Android 15 emulator transfer/receipt run. `Cargo.toml:20-26` explicitly excludes the Lean producer/archive path, so this proves the Rust verifier/apply core cross-compiles, not full verified production on Android.
- `breadstuffs/mobile/deos-android-paint/` is a Rust `cdylib` NativeActivity APK generated by cargo-apk. It pins the gpui Android fork at `adb9026524`, targets arm64, min SDK 28/target 34, and enters through `src/lib.rs::android_main`. `mobile/README.md:63-77` says renderer initialization reached a Vulkan surface but emulator GPU paths did not produce a clean frame; a physical-device run and an Android Lean archive remain open. This is dated documentation, not a fresh run.
- `breadstuffs/android-cell/` is a Rust capability/runtime model and ADB emulator adapter, not an Android app host. `src/checkpoint.rs:31-47` explicitly limits checkpoints to the observable boundary, excluding guest RAM/process/Binder state. `tests/live_emulator_spike.rs` is an ignored, approximately two-minute macOS/AVD integration test for frame capture and capability gates.
- `breadstuffs/starbridge-v2/src/systemui_caps.rs` and `src/bin/systemui_cap_bake.rs`, behind the `android-systemui` feature (`Cargo.toml:176-186`), model SystemUI/cockpit capability chrome on the host. They are not an AOSP SystemUI integration.
- `breadstuffs/dregg-lean-ffi/build.rs` contains generic native/static/shared linking machinery, but no demonstrated Android Lean archive port. `/tmp/dregg-android-runtime-contract-review.md` also identifies the node’s process-owned `run(Cli)` and missing stoppable host handle as the shared cloud/mobile blocker.
- No AndroidManifest/Gradle/Kotlin/JNI product target was found in `minidregg`, `DreggNet`, `DreggCloud`, or `dregg-infra`. DreggCloud lockfile Android dependencies are transitive, not an app. Minidregg’s native adapters are child-process SQLite/Ed25519 tools, not JNI.

An Android product can later be an adapter over the same reusable node-host lifecycle used by the cloud supervisor. Today, assigning “embed the full node in Android” would include unresolved host extraction, cross-target Lean linkage, durable restart, UI/platform integration, and physical-device validation—too many contracts for one legible first feature.
