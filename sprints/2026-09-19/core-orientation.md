# September 19 — deeper Bread/Mini orientation after the implementation pause

**Current operating mode: investigation and discussion.** Ember rejected introducing Python as a new platform implementation language and asked us to investigate before another implementation swarm. The later request authorized a microswarm on Bread and Mini. The earlier [implementation record](implementation.md) is historical; its Python choice, active assignments and settled Mini selection do not describe current authorization.

Two Astra investigators traced Bread execution and Mini semantics; one Sol investigator traced Mini deployment. Root checked the consequential source paths and external-operation records. This pass ran no builds, tests, services, remote jobs or asset operations, and changed no Bread/Mini source. Source inspection, prior captured runs and proposed construction are separated below. The adjacent [inventory](core-orientation-sources.json) captures current source bytes, including uncommitted WIP; a repository HEAD alone does not identify that WIP.

## Recommendation, still a proposal

Make Mini's canonical receiver the leading candidate for the resource system, and evaluate Bread components individually as operational machinery and reference implementations. Mini better matches the accepted policy/grant semantics and the founding requirement that source-derived meaning have one authoritative execution path. This is a reason to invest in its core, not evidence that it is already deployable.

The proposed deliverable is a programmable resource world with hosted Hermes as a participant: users author laws, propose operations, delegate rights, share content and run budgeted tasks. A grain should have canonical task, authority, allowance, attempt and result records. A host-side application with only a four-number kernel anchor would not provide that world.

House is not the default architecture. Ember explicitly questioned its independence and quality. Its `Machine` owns a separate state model; portions of fork/suspend/resume manipulate records rather than processes. Reuse must be justified component by component. This investigation does not retire Bread or endorse a wholesale port.

## Specific apparent functionality that needs repair

1. **Factory deployment through the legacy node MCP tools is not real deployment.** `node/src/mcp/handlers_apps.rs:5` hashes a descriptor, stores nothing, and returns `deployed: true`. The legacy hosted creation tool at line 79 returns `created: true` without creating a cell. A newer effect-based tool exists. In contrast, World's ordered factory deployment and the executor's factory child creation are substantive. Choose the real path and complete user-authorized deployment.
2. **Bread's policy replacement conflicts with the accepted self-management rule.** `apply_set_program` stores the replacement (`turn/src/executor/apply.rs:1418`); later validation reads the new policy (`execute_tree.rs:655`). `None` skips that check. The old snapshot is cell state, not the prior policy. Source ordering therefore does not require the previous policy to approve its removal. This is a source-derived finding, not a newly executed counterexample.
3. **Current exposed reads are not a tenant disclosure contract.** The node cell-detail endpoint returns program, fields and capability data without a read-authority check (`node/src/api.rs:6347`); the World bridge exposes full-ledger access. JS's local capability table does not repair those receiver boundaries. Private resources need authorized observation as well as authorized writes.
4. **A tool-intent receipt is not an execution result or an exact request commitment.** `deos-hermes/src/tool_effects.rs:49` uses FNV-1a over strings. File-write events record path digest/prefix and content length, not the content bytes. `run_js` similarly records a noncryptographic digest and length. These events cannot substantiate the intended exact authorized request or actual external outcome.
5. **Existing durable settlement has an ambiguity worth avoiding.** `hosted-durable/src/settle_ledger.rs:70,168` records an unconfirmed reservation, then replays it through the same receipt type as a confirmed settlement. Its conflict check compares amount/asset, not payer/beneficiary; those identities are absent from the record. `durable_settlement.rs:156` returns replay without dispatch. This prevents repeat submission in that path, but does not expose a completed-versus-uncertain outcome. It is not a ready generic provider-operation protocol.

## Mini's unfinished work is concrete

The scalar page is one current materialization, not the fundamental limit of `CellState`. Typed content, links, transclusion and annotation semantics already exist in `Theory/HyperdocumentOperations.lean`; native selection and materialization must make them executable and observable. The initial registry is a closed, source-defined set of kinds. Runtime schema authorship is a design choice still to make.

Similarly, `MultiCellHyperedge` already derives exact prepared patches and requires all incidences to accept. The new work is a public joint declaration that uses it, derives one combined final patch per physical cell, and evaluates laws and authority against those exact posts. Do not report the current single-target invocation restriction as absence of multi-cell semantics.

`Pred` currently compares slots to constants, checks finite membership/write-once/monotonicity, and composes these with Boolean operations. The paused resource projection derives before/after/delta and pairwise delta slots. That enabled real grain budget/lifecycle laws, but endlessly adding application-specific derived slot names would create another specialization problem. Consider a small typed expression language, with semantics and lowering through the existing compiler, when specifying the next resource laws.

`AgentGrain` currently models generation/status/remaining/reserved. These are permission allowances, not funded Book balances or $DREGG. It is a useful law specimen, not a complete grain: typed prompts/results, attempts, allocation relationships and resource references must also have canonical meaning. `IrreversibleEffectSettlement`, reactive terminal and outbox semantics provide foundations for explicit performed/refused/uncertain outcomes; their physical handlers and current native receivers remain work.

## Deployment and measured evidence

Current `Host/Main.lean` exposes a sequential framed stdio service and file CLI, with 1 MiB frame limits. It is a local authoritative receiver, not an already networked node. Each ordinary request reopens and semantically replays history. The SQLite helper stores one opaque image (64 MiB bound) and rewrites it with exact CAS. Confirmation reopens again. This is a serious growth cost, not a reason to weaken replay validation.

A runnable alpha needs the actual current host linked and the public BabyBear/scalar-29 CLI journey exercised. The executable was absent in the inspection; the latest public CLI journey remains unrun. Existing `.olean` files do not substitute for an exact-source acceptance record. The paused Python build/bootstrap helpers are preserved WIP, not endorsed next commands.

For sustained use, instantiate source-derived checkpoint/suffix recovery and indexes for actual signed ingresses and historical receipt identities. Validate the checkpoint's authority and semantic relation to retained history; do not trust an arbitrary cached tip. `DurableWalHandler` and framed-WAL laws are useful foundations, not a drop-in current store. Contention must cause re-prepare/re-sign where authority or clock observations change; generic blind retries are explicitly forbidden.

The strongest retained Mini journey exercised paid birth, owner use, two policy changes preserving grants, new-rule refusal, narrower Alice-to-Bob delegation, Bob's signature, SQLite reopen and expired exact retry. It used ZMod65537/scalar15, public fixture keys and Lean IR, predating current controller factoring/profile. Its ~535 seconds is not linked-host latency. See [the retained handoff](../2026-09-18/wind-down/artifacts/dregg-resume-journey-handoff.md).

Bread's retained factory/history journey passed constructor → child mutation → checkpoint → later deployments → reopen → historical forks. Its factory had no state constraints and the mutation was an allowed incoming transfer. That supports durability, not complete authenticated user-authored policy execution. See [the runtime checkpoint](../2026-09-18/wind-down/artifacts/dregg-resume-runtime-checkpoint.md).

Peer replication, migration and participant hosting need real authenticated transport, epoch/membership rules, catch-up, destination admission and transfer/freeze semantics. Existing models are relevant, but a replicated service was not found in the current host closure. A first single-authority deployment can exercise real resource semantics while keeping that expansion explicit; this is a proposed staging choice, not a waiver of the participant-node goal.

## What to build, in dependency order

1. **Specify one shared resource journey and its wire contract.** Two principals create a room and typed content, install/change its laws, delegate a narrower right and make an atomic change across content/task/index. Unauthorized reads and writes refuse. Revocation takes effect. A restart and exact retry preserve the original result. This is an acceptance specimen for the general system, not a fixed application genre.
2. **Complete the canonical resource surface.** Typed payloads/references and source-owned schemas; general joint declarations; scoped observations; revocation/key changes; the needed predicate expressiveness. Program authoring and operation submission must reach these same semantics.
3. **Make external work a resource lifecycle.** An exact request names authority, generation, budget reservation, provider/tool target and immutable input. An attempt records dispatch and an explicit result/refusal/uncertainty. Publication can atomically update result, task and shared index. Kernel acceptance cannot itself stop a remote API or prove its cost; the handler must supply appropriately scoped evidence.
4. **Operate the actual receiver and host it in Rust.** Finish linked-host acceptance, durable client outbox, supervision, bounded storage/recovery, connection leases and custody. Reuse reviewed Bread transport/isolation/secrets machinery. Preserve physical interruption independently of a slow kernel request; reconcile its canonical outcome before reopening execution.
5. **Attach actual upstream Hermes and a programmable shell.** Expose inspect/author/propose/commit/observe with retained operation identities. General client code can compute proposed actions while installed laws determine admissibility. If we promise installed executable functions, define and implement that separately; a field called `programCode` does not provide it.

Core work and hosting work can run concurrently once these contracts are agreed, integrating through this same journey. Full STARK assurance can follow functioning native semantics; the protocol must retain profile/version and evidence scope. TLSNotary/request certificates need exact request construction and response-consumption binding, not just the current intent events. Solana utility and contributed-provider stake remain accepted goals with a still-unselected concrete economic operation.

The next discussion should settle the resource/program contract and first deployment scope. The proposal favors Mini, but does not resume implementation or settle every open choice by writing it here.
